## 1. プロジェクト名

**期限みまもり 店舗版**（仮称）

## 2. 目的

小規模食品小売店が、期限の近い商品を探す時間と値引き・撤去の見落としを減らす。食品安全や売上を自動保証する製品ではなく、店舗が決めた期限対応を確実に実行するための確認支援ツールとする。

## 3. 対象ユーザー

- 1店舗あたり1〜10人程度で運営する独立系食品小売店、菓子店、地域売店、食品セレクトショップ。
- 賞味・消費期限のある商品を扱い、現在は棚の目視、期限シール、紙、または表計算で確認する店舗。
- 最初の実証は、共有端末1台で期限確認を完結できる店舗に限定する。

大手チェーン、POS統合が必須の店舗、食品製造工程全体の管理を求める事業者はMVP対象外。

## 4. 現在の問題

1. 棚全体を見回らないと、今日対応すべき商品が分からない。
2. 同じJANでも入荷ごとに期限が違い、商品マスタだけでは期限を管理できない。
3. 紙や表計算では、値引き・撤去・確認済みを担当者間で追いにくい。
4. 高機能な在庫・現場管理製品は、期限確認だけを必要とする小規模店には導入が重い可能性がある。

この問題の頻度・費用は未検証であり、5店舗の実作業観察で確認する。

## 5. 解決方法

JANを読んで既知の商品名を呼び出し、入荷ロットの期限を登録する。アプリは日付順の全件表示ではなく、「期限切れ」「今日対応」「7日以内」を行動リストとして表示する。担当者は値引き、撤去、確認済みを記録する。

検討した代替案:

- **A: 既存アプリに期限ロットと対応一覧を追加** — 最小で価値の中心を検証できるため採用。
- **B: 表計算テンプレートだけを提供** — 開発前の課題検証には使うが、JAN再利用と当日抽出の操作性を検証しにくい。
- **C: POS・クラウド同期まで実装** — 導入障壁と費用が高く、MVPでは不採用。

## 6. 提供価値

- 期限確認で棚・表を探す時間を減らす。
- 値引きできる期間を逃す見落としを減らす。
- 「誰かが見たはず」をなくし、対応済みかを端末上で確認する。
- 新しい大規模システムを導入せず、スマートフォンまたはタブレットから始める。

## 7. 競合

- 紙の期限チェック表、期限シール、表計算。
- POS・在庫管理システムの期限／ロット機能。
- スマートマットクラウド等の在庫自動化。
- カミナシ等の現場帳票・点検デジタル化。
- HACCP記録アプリ。

公開情報の整理は `RESEARCH_STATE.md` を参照する。実証候補が使っている具体的製品と見積額は、一次調査で追加する。

## 8. 差別化

- 対象を「小規模1店舗の期限ロット確認」に絞り、初期設定なしで使える。
- JANは在庫数量を自動取得する魔法の鍵ではなく、商品名の再入力を省くために使う。
- 機能の多さではなく、「今日見るものがすぐ分かる」「登録が10秒以内」を競争軸にする。
- 外部APIを使わず端末内で開始でき、写真を送信しない。

## 9. MVP機能

### P0（開発移行が承認された場合に絶対に必要）

1. **期限ロット登録**
   - JAN-8/JAN-13のカメラ読取または手入力。
   - JANなし登録。
   - 商品名、期限日、数量（任意）、棚・保管場所（任意）。
   - 同じJANの商品名を再利用するが、期限は毎回入力する。
2. **対応リスト**
   - 期限切れ、今日から3日以内、7日以内、それ以降。
   - 未対応を先にし、期限が近い順にする。
3. **対応操作**
   - 「確認済み」「値引き済み」「撤去済み」のいずれかを記録。
   - 誤操作を取り消せる。
4. **編集・削除・端末内保存**
   - 保存失敗時に成功表示をしない既存方針を維持。
5. **店舗利用上の注意**
   - データはこの端末・ブラウザー内だけで、ブラウザーデータ削除時に消える。
   - アプリは食品安全、期限設定、法令適合を保証しない。

### P1（P0の実証中に必要性が確認されたら追加）

- CSVによる手動バックアップ／復元。
- 対応履歴の直近30日表示。
- 店舗ごとに「値引きを始める日数」を設定。
- 同一商品・同一期限の数量まとめ。

### P2（有料意思の確認後）

- 複数端末同期と担当者名。
- 複数店舗ダッシュボード。
- メール／プッシュ通知。
- POS・発注連携。
- 廃棄・値引き額の分析。

## 10. MVPでは作らないもの

- 課金処理、有料契約。
- AIによる期限日・商品名の完全自動認識。
- 自動発注、需要予測、価格自動決定。
- HACCP全帳票、法令適合判定。
- 外部画像API、広告SDK、分析SDK。
- アカウント、権限管理、クラウド同期。
- GS1/GTIN-14の読取。

## 11. ユーザーフロー

1. 店舗の共有スマートフォン／タブレットでアプリを開く。
2. 入荷時または初回棚確認時にJANを読む。
3. 初回だけ商品名、毎回期限日を入力し、必要なら数量・棚を追加する。
4. 開店時または期限確認時に「今日対応」を開く。
5. 現物を確認し、値引き・撤去・確認済みを記録する。
6. 閉店時に未対応がないかを見る。
7. 週末に、従来の確認時間・漏れと比較する。

## 12. 成功指標

### 問題検証ゲート（実装前）

- 5店舗中3店舗以上で、期限確認が週60分以上、または直近1か月に対応漏れ・廃棄がある。
- 5店舗中3店舗以上が既存手段の具体的不満を実演できる。
- 10商品の模擬登録で中央値15秒以下を達成できる見込みがある。

### 4週間MVP

- 登録時間中央値10秒以下。
- 参加2〜3店舗のうち3分の2以上が4週目も自発利用。
- 期限確認時間30%以上削減、または対応漏れ50%以上削減。
- データ消失・誤った成功表示が0件。
- 半数以上が月額1,980円で継続を検討し、得られた価値を具体的に説明できる。

## 13. 中止条件

- 5店舗中4店舗以上で問題が週30分未満かつ金銭損失もほぼない。
- 既存のPOS・紙で十分で、明確な未解決作業がない。
- 2週目以降の利用が対象営業日の30%未満。
- 改善後も登録中央値が20秒を超える。
- 月額1,000円でも申込意思がなく、測定効果も価格を下回る。
- 食品安全上、ツールの誤用リスクを許容範囲まで下げられない。

## 14. 技術的前提

- 現行のHTML/CSS/JavaScriptのみのPWA相当Webアプリを土台とする。
- JAN検証、端末内カメラデコード、`localStorage`、保存失敗時のロールバックを再利用する。
- データモデルは「商品」と「期限ロット」を明確に分ける。MVPで移行が必要な場合、既存データを削除せず後方互換で読み込む。
- 外部依存・サーバー・有料サービスは追加しない。
- Nodeの自動テストに、同一JAN複数期限、対応状態、並び順、保存失敗、旧データ移行を追加する。
- 実機カメラの既知限界（曲面、傷、反射、GS1/GTIN-14非対応）を維持する。

## 15. 想定価格

仮説: **1店舗 月額1,980円**。4週間の実証は無料とする。クラウド同期なしの端末内版に継続課金できるかは特に不確実なため、課金実装より先に書面で継続申込意思を確認する。

## 16. 収益モデル

将来は店舗数課金の月額または年額SaaS。複数端末同期が価値の中心と判明した場合のみ、運用原価とプライバシーを再評価して別プランを検討する。広告と食品関連アフィリエイトは、現場の信頼と操作集中を損なうため採用しない。

## 17. 検証方法

1. 食品小売5店舗の実作業を観察し、直近の事実を聞く。
2. 既存アプリまたは紙プロトタイプで10商品を登録してもらう。
3. 条件を満たす2〜3店舗だけで4週間使う。
4. アプリ内の複雑な分析機能は作らず、週次に開始・終了時刻、登録件数、漏れ、廃棄を計測表へ記録する。
5. 終了時に「無料なら使うか」ではなく、月額1,980円の申込書を提示して判断してもらう。実際の課金・公開はユーザー承認後に行う。

## 18. リスク

- **市場**: 課題は存在しても頻度・金額が課金水準に届かない。
- **利用**: 入荷ごとの期限入力が面倒でデータが古くなる。
- **技術**: 端末内保存は複数担当に共有できず、ブラウザーデータ削除で消える。
- **運用**: 問い合わせや商品マスタ整備が収益を上回る。
- **安全・法務**: アプリ表示を安全保証と誤解される、または店舗ルールの誤設定をアプリの判断と誤認される。
- **競争**: POSや既存DX製品のオプションで十分な場合がある。
